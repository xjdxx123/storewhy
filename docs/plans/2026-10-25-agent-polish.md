# StoreWhy Agent 打磨计划

日期：2026-10-25。状态：阶段 1、1A 与阶段 2 工程实现及验证已完成；阶段 3 与 UI 联调待执行。阶段 2 逐题材料供团队业务验收。UI 仍由队友负责，主会话负责 TypeScript 后端。

目标：让运营人员从一次调查中看懂最值得关注的变化、支撑解释的证据、尚未解决的问题，并能顺畅追问。沿用现有六类问题和现有数据范围。

## 初始验收基线

- 初始实现基准：1022e26，已 push 至 GitHub。后端和 Zetaris、Nightshift 连接正常。
- 50 项自动化测试通过；44 项 Live 用例通过，另有 12 轮加强追问检查通过。
- 44 项评测主要断言状态、分析范围、必需指标、Why 目标保留和事实绑定；其中 3 个用例执行了 Reviewer。这个通过率不等于解释质量已经全面验收。
- 实际 Why 回答的 summary 仍是通用语句；checkedExplanations 只列整体/分组；nextSteps 为通用提示。模型选择的事实已有证据，但呈现尚未清楚区分主线、机制和缺口。
- 44 项记录中，3 个有 Reviewer 的用例中位耗时约 37.2 秒，简单有查询用例约 7.8 秒；HTTP 主调查一次约 63.6 秒。60 次模型调用包含 5 次 JSON 修复；最高单轮耗时约 132.8 秒。
- 证据来源：evidence/why-example.json、evidence/agent-evaluation.json、evidence/followup-evaluation.json、evidence/http-agent-smoke.json；实现来源：apps/server/src/agents/engine.ts、scripts/evaluate.ts。

## 阶段 1：回答直接解决用户的问题（P0，已完成）

工作：

- 将摘要改为本次问题的具体结论，优先呈现最相关的渠道和变化，再展开证据。
- 输出层次为：一句结论、2—3 条关键证据、已检验的解释、尚未解决的缺口、可继续执行的追问。
- 金额和比例仍由已执行结果生成；模型选择证据和解释结构，新增文字中的事实同样必须校验引用。
- 渠道金额变化可加总，检查增量与抵消关系；用户数、付费率、每付费用户收入用于进一步调查，不把它们直接包装为广告因果贡献。
- 下一步建议依据当前缺口生成完整问题并携带可校验的分析条件。避免重复已完成的检查；每条建议仍需经过数据能力校验。
- 共享契约采取向后兼容的新增字段，保留现有 Answer 与 SSE 用法，更新 frontend-integration 文档和一个脱敏 payload 样例，便于队友同步展示。

Done definition：

- 主案例的首句明确指出 TipTop 的费用/收入变化，不再仅说“已通过审查”。结论来自当前查询，换时期或渠道后不得复用固定答案。
- 每条关键结论可追溯至 evidenceId/factId；金额与独立参考一致；反向变化不被描述成下降。
- 至少两条追问可经现有接口实际执行，保留未修改的时期、人群、筛选与窗口。
- 旧 client 仍能读取结果，新增字段有契约测试；现有 tests、lint、typecheck、build 通过。

### 阶段 1 验收记录

## 阶段 2：验证并补强 Why 调查深度（P0，工程验收完成）

工作：

- 根据问题选择待检验解释：用户规模、付费比例、每付费用户收入、首次/复购收入、渠道构成、观察期成熟度。
- 保存每条解释的证据和状态：受到支持、受到反证、缺少数据、尚未检查。没有执行对应查询时，不宣称排除了该解释。
- 优先检验提问前提。例：切到 FaceBoom 后，可能应先指出费用下降且收入上升，而不是继续沿用整体费用上升的前提。
- Reviewer 针对具体证据缺口要求补查；沿用查询预算、筛选限制和确定性数值校验。增加解释记录不意味着每轮执行全部分支。
- 新增 8 个未用于调 prompt 的 Why 问题和 2 个前提错误/数据不足的反例，覆盖至少三种时期或渠道组合；另检查两组各三轮追问。
- 单独评估回答质量：是否正面回答问题、是否找到相关结构变化、证据是否充分、是否清楚披露未验证部分、下一步是否可执行。自动核对事实，人工审阅解释。

Done definition：

- 独立数值核算和所有旧回归通过；新用例保留逐题结果，合理的 limited/unsupported 与完成状态分别记录。
- 至少验证一条需要 Reviewer 补查的路径、一条推翻用户前提的路径、一条因数据缺失而停止的路径。
- 支持/反证状态均绑定已执行证据；新增用例没有无依据的金额、趋势或因果断言。
- 简单问题无需为了展示 Agent 而强行增加调查轮数。

### 阶段 2 执行清单（2026-10-25）

## 阶段 3：减少等待，解释执行状态（P1）

工作：

- 先记录每轮意图解析、SQL、解释、Reviewer、格式修复的分段耗时，定位实际瓶颈。
- 将现有 SSE 映射为用户能理解的进度，例如“正在比较两个时期”“正在检查渠道差异”“发现证据不足，正在补查”。进度仅报告真实事件，不输出模型内部推理。
- 针对实际瓶颈缩短重复输入、改善 JSON 契约表达、减少不必要的修复和重复查询；保留 Why 的审查和证据校验。
- 沿用严格匹配数据版本与分析规格的去重；跨请求缓存如有必要再引入，必须展示来源和时间。
- 检查取消、模型超时、Zetaris 离线、刷新恢复与重复提交的用户反馈；Live 错误仍显式返回。

Done definition：

- 主案例至少五次同条件执行，对比总耗时、模型/SQL 次数和格式修复次数；披露样本量和长尾。
- 本地请求能及时收到首个进度事件；执行中的用户可见状态与实际阶段一致。
- 优化后通过阶段 2 的正确性检查；取消、异常、恢复路径有可重复的验证记录。

## 阶段 4：与队友完成真实 UI 联调和 Demo（P0，UI 就绪后）

分工：后端提供稳定 contracts、结果样例、SSE 和错误状态；队友实现 React 页面；双方共同进行浏览器验收。

页面最小交付：

- 始终可见的时期、用户范围、窗口与筛选条件。
- 一句结论、关键指标和渠道比较；证据可以展开查看定义、SQL 与 queryId。
- 可点击追问、真实调查进度、取消和失败状态。
- 明确区分 Live、教学数据和录制/fixture 回放。

Done definition：

- 浏览器连续完成主 Why → 只看指定渠道 → 切换 7 天 → 一个数据缺失问题；条件与新证据一致。
- 展示一次 Reviewer 要求补查和一次有来源的记忆偏好恢复。
- 团队预演三分钟 Demo，记录真实耗时；正式录屏和赛事提交按团队安排进行。

## 执行顺序与时间不足时的取舍

1. 先完成阶段 1A 的图表数据契约和证据绑定，让队友按真实 payload 开发；再继续阶段 1 的具体结论与推荐追问。
2. 完成阶段 2 的 Why 质量检查，按失败案例做必要修复。
3. 根据阶段 3 的计时证据实施有收益的性能优化。
4. UI 一旦可用即开始阶段 4，联调发现的阻断问题优先修复。

剩余时间紧张时，优先交付具体结论、证据引用、两条可执行追问和完整浏览器主流程。新增平台、任意数据上传、广告账户操作和更换记忆引擎留到后续版本。
