# Demo 脚本与提交材料草稿

队友仅录屏可用 [共享后端](shared-backend.md)，保存私有连接文件后执行 `npm run demo:ui`。自己运行整套服务时先按 [录屏指南](recording.md) 配置，再用 `npm run demo` 同时启动 API 与备用 React UI。

实际录屏以 [已验证的英文问题与顺序](recording-questions.md) 为准。下面保留赛事介绍与讲解结构。

## 三分钟演示

1. **场景，二十秒**：运营人员看到渠道费用上升，但新用户收入没有同步增长。普通报表展示数值，StoreWhy 帮助提出和检查解释。声明这是 Procrastinate Pro+ 公开教学快照。
2. **真实 Why，约八十秒**：提问“为什么2019年7月比6月费用增加，获客后14天收入却没有同步增长？”展示当前 paid/cohort/14天条件、Zetaris 证据与调查进度。展开实际执行的 SQL 与 queryId；只在这轮确实发生补查时演示补查。
3. **追问，约四十秒**：“Focus on FaceBoom”，再“Use 7 days”。展示条件更新、证据 ID 变化和重新计算。可将七天保存为会话默认，再开始新分析，说明临时渠道不会自动沿用。
4. **能力边界，二十秒**：“是不是素材疲劳导致CTR下降？”系统解释缺少点击/曝光/素材字段，不能编造结论。
5. **Sponsor 与价值，二十秒**：Zetaris 负责实际数据分析；Nightshift 路由 NVIDIA 模型；H-MEM 保留有来源的偏好、纠正与审计。强调输出包含已核查事实、有限解释和下一步。

录制前通过 `/integrations` 核对连接，预跑一次主问题并检查延迟。若供应商失联，只能展示明确标注的自制 fixture 回放，不能称为 Live Agent。备用 React UI 已可用于录屏；正式视频与截图由团队录制。

## Slides 内容

- 问题：增长团队缺少从“发生了什么”走向“为什么”的可检查调查过程。
- 产品：在明确数据范围内自由提问，按证据补查，承接多轮追问。
- 架构：React → TS API → Investigator / Reviewer → Zetaris；Nightshift/NVIDIA 与 H-MEM。
- 验证：独立数值基准、真实 SQL、固定/改写问题、多轮条件与故障测试；展示最新运行验证与逐题材料，区分 completed、limited、unsupported，不把状态通过率当作广告因果解释正确率。
- 边界与下一步：真实数据连接、多平台口径校准、授权与部署；当前没有证明广告因果或提供预算优化。

## 发布前由团队完成

仓库目前为 private；如赛事要求公开，需要用户明确授权后调整。Why 可靠性优化及接入文档已按授权 push。后续运行优化本地交付；队友 React UI 接入与验收、团队预演、视频录制上传、slides 文件制作及正式提交仍需团队完成或另行授权。这份文件是本地可检查的内容草稿。

## 运行优化后的预演方式（API 1.4.0）

先执行 `npm run demo:check`。它只检查当前 API、Zetaris/Nightshift 连接、Vite CORS 与数据披露，不创建 Agent 调查，也不发布或提交任何内容。

自动联调可执行 `npm run test:browser:live`：真实 Chrome 完成主 Why（中途刷新恢复）→ FaceBoom → 7 天 → 保存/恢复偏好 → 取消一轮 → 一个独立 Reviewer 补查问题 → 缺少 CTR 数据。截图与逐步实际状态写入 evidence/browser-live*。这是一套后端契约的完整排演工具，包含的验证步骤多于正式三分钟 Demo；不等同于队友 React 页面或团队预演。

正式演示时，以主 Why、一次渠道/窗口追问、一次能力边界为主。普通用户看到真实阶段 label，不展示模型自由理由或工程计时。可在详情展开 SQL、queryId、图表逐点来源。若主问题首查已足够，不为了展示 Agent 强行要求补查；要演示 Reviewer 补查可用：

> 为什么 FaceBoom 在 2019 年 8 月相较 7 月新用户首周购买用户比例不同？只检查行为，不分析广告费用。

计时以本机最新实测为准，保留供应商延迟余量。已保存的偏好只作带来源的口径恢复，临时渠道筛选不自动成为长期偏好。正式录屏、队友 React 页面验收、团队业务判断与赛事发布仍需团队完成；仓库可见性没有改变。
